# PRODUCT.md

## 1. Проблема и целевая аудитория

### Проблема
Пользователь теряет контроль над регулярными платежами за цифровые сервисы: подписки оформляются в разные даты, могут иметь одинаковую или изменённую стоимость, а отмена часто требует отдельного входа в сервис.

MVP решает задачу через Telegram: после подключения банковских данных бот анализирует историю операций, выявляет вероятные регулярные подписки по повторяемости платежей, получателю/назначению и стоимости, показывает найденные подписки и помогает перейти к их отмене или инициировать отмену там, где доступна официальная интеграция.

### Целевая аудитория
- Частные пользователи с несколькими платными цифровыми сервисами.
- Пользователи, которые хотят быстро найти забытые или редко используемые подписки.
- Пользователи, предпочитающие Telegram единому интерфейсу управления регулярными расходами.

Первый MVP ориентирован на пользователей Сбербанка и сервисы, для которых возможно безопасно получить подтверждение подписки и способ её отмены.

## 2. Основной пользовательский сценарий

1. Пользователь открывает Telegram-бота.
2. Бот идентифицирует его по Telegram ID.
3. Пользователь запускает подключение Сбербанка через официальный поддерживаемый механизм авторизации/интеграции.
4. Пользователь даёт необходимые разрешения на чтение операций.
5. Бот получает ограниченный период истории операций.
6. Система нормализует операции и ищет регулярные платежи: повторяемость, близкие даты, одинаковую/похожую сумму и устойчивого получателя.
7. Бот формирует список вероятных подписок с уровнем уверенности и объяснением, почему операция была распознана как подписка.
8. Пользователь открывает карточку подписки.
9. Если сервис поддерживает реальную отмену через интеграцию, бот предлагает инициировать отмену и получает подтверждение результата.
10. Если прямой API отмены отсутствует, бот показывает официальную страницу/инструкцию отмены.
11. Бот фиксирует результат операции и обновляет состояние подписки при следующем анализе.

## 3. Функции MVP

### Telegram
- Идентификация по Telegram ID.
- Главное меню.
- Список найденных подписок.
- Карточка подписки.
- Запуск повторного анализа.
- Уведомление о необходимости переподключить банковский доступ.
- Подтверждение потенциально необратимого действия перед отменой.

### Подключение банка
- Интеграция со Сбербанком только через официальный разрешённый механизм.
- Получение операций без хранения логина, пароля, SMS-кодов или иных банковских секретов.
- Ограничение периода запрашиваемой истории.
- Отзыв/удаление банковского подключения пользователем.

### Поиск подписок
- Нормализация получателя платежа.
- Группировка операций по вероятному сервису.
- Анализ периодичности.
- Анализ одинаковой или близкой стоимости.
- Учет небольших отклонений суммы.
- Отсечение разовых и явно нерегулярных покупок.
- Расчёт confidence score.
- Отображение основания, по которому платёж признан подпиской.

### Экономия и дублирование подписок
- Анализ найденных подписок на предмет функционального пересечения.
- Группировка сервисов по предполагаемому назначению/категории.
- Выявление пар или групп подписок, которые могут решать похожую задачу.
- Показ пользователю объяснения, почему подписки считаются потенциально дублирующими.
- Оценка потенциальной экономии при отказе от одной из подписок.
- Ненавязчивые рекомендации: проверить использование, выбрать одну подписку или перейти на более подходящий тариф.
- Рекомендации должны быть явно обозначены как предположение, а не как финансовый совет или гарантированная экономия.

### Отмена
- Реальная отмена через официальный API/интеграцию там, где она доступна.
- Переход на официальную страницу отмены там, где API отсутствует.
- Отображение статуса результата.
- Защита от повторного случайного запуска отмены.

### Минимальное хранение
- Telegram ID.
- Идентификатор банковского подключения в обезличенном/техническом виде.
- Нормализованные данные, необходимые для работы подписок.
- Состояние подписки и результаты операций отмены.
- Минимальные технические журналы без банковских секретов.

## 4. Что не входит в MVP

- Поддержка всех российских банков.
- Автоматическое распознавание абсолютно любых сервисов с гарантией 100%.
- Хранение банковских логинов, паролей или кодов подтверждения.
- Управление банковскими счетами, переводами, платежами или кредитами.
- Автоматическая отмена подписок через неофициальные методы, эмуляцию сайта или обход защиты сервиса.
- Оплата подписок или их перенос на другую карту.
- Семейные/корпоративные аккаунты и совместное управление.
- Полноценное мобильное/web-приложение.
- Полноценное персональное финансовое консультирование, требующее доступа к данным, которых нет в подключённых источниках.
- Персональные рекомендации по расходам и потенциальной экономии на основе обнаруженных регулярных платежей.
- Поиск практически повторяющихся подписок и сервисов: выявление подписок с пересекающейся функциональностью или похожим назначением, чтобы показать возможное дублирование расходов.
- Сравнение таких подписок и предложение вариантов экономии, например: отказаться от одной из дублирующих подписок, перейти на более дешёвый тариф или проверить необходимость сохранения сервиса.
- Обещание отмены в случаях, когда сервис не предоставляет подтверждаемого способа отмены.

## 5. Проверяемые критерии готовности

MVP считается готовым к тестовой эксплуатации, если:

1. Новый пользователь может пройти путь Telegram ID → подключение банка → анализ операций без ручного вмешательства команды.
2. Система корректно обрабатывает как минимум заранее определённый тестовый набор регулярных и нерегулярных операций.
3. Для тестового набора подписок система показывает ожидаемый сервис с приемлемой точностью, а ложные срабатывания не блокируют пользователя.
4. Для каждой найденной подписки пользователь видит сумму, примерную периодичность, последнюю операцию и основание распознавания.
5. Для интегрированных сервисов отмена проходит через официальный API и результат подтверждается системой.
6. Для остальных поддержанных сервисов доступна официальная страница отмены.
7. Перед отменой требуется явное подтверждение пользователя.
8. Банковские секреты не сохраняются в приложении.
9. Пользователь может удалить/отозвать банковское подключение.
10. Ошибки банка, сервиса или сети приводят к понятному сообщению и безопасному состоянию без ложного сообщения об отмене.
11. Есть автоматические тесты критических правил распознавания и интеграционных сценариев.
12. Система пригодна для дальнейшего добавления банков и сервисов без переписывания ядра продукта.

## 6. Технические и организационные ограничения

- Telegram является основным пользовательским интерфейсом.
- Telegram ID используется как идентификатор пользователя; отдельная регистрация не требуется.
- Банковская интеграция должна использовать только официальный и юридически допустимый механизм доступа Сбербанка.
- Архитектура должна разделять банковский коннектор, движок обнаружения подписок и коннекторы отмены сервисов.
- Нельзя строить MVP на хранении банковских учётных данных пользователя.
- Все действия с отменой должны быть идемпотентными либо защищены от повторного запуска.
- Доступ к данным должен быть минимальным по принципу least privilege.
- Секреты интеграций хранятся отдельно от бизнес-данных.
- Обработка персональных и финансовых данных требует отдельной оценки требований применимого законодательства и политики поставщиков API до публичного запуска.
- Для MVP желательно ограничить список реально поддерживаемых способов отмены несколькими сервисами, а не пытаться сразу поддержать рынок целиком.

## 7. Риски продукта

| Риск | Влияние | Митигирование |
|---|---|---|
| Нет доступного официального API Сбербанка для нужного сценария | Критическое | До разработки подтвердить конкретный канал интеграции, права и ограничения |
| Нет API отмены у большинства сервисов | Высокое | Архитектурно разделить discovery и cancellation; использовать официальные страницы отмены |
| Ложные срабатывания при распознавании подписок | Высокое | Confidence score, объяснение причины, порог уверенности и подтверждение пользователем |
| Сервис меняет merchant descriptor или сумму | Среднее/высокое | Нормализация получателя, допуски по сумме, история группировки |
| Пользователь считает найденную подписку ошибочной | Среднее | Показывать доказательства распознавания и позволять скрыть результат |
| Ошибка отмены воспринимается как успешная отмена | Критическое | Явные статусы: «запрос отправлен», «подтверждено», «не подтверждено», «недоступно» |
| Изменение API банка/сервисов | Высокое | Адаптеры, контрактные тесты и мониторинг интеграций |
| Утечка финансовых данных | Критическое | Минимизация хранения, шифрование, изоляция секретов, аудит доступа |
| Юридические ограничения на обработку финансовых данных | Критическое | Правовая проверка до тестирования на реальных пользователях |
