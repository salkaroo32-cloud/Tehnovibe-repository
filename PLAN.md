# PLAN.md

## 1. Этапы реализации и зависимости между ними

### Этап 0. Проверка реализуемости интеграций
**Зависимости:** нет.

- Подтвердить конкретный официальный механизм доступа к операциям Сбербанка, права, формат данных, лимиты и требования к приложению.
- Проверить допустимость хранения и обработки нужных данных.
- Выбрать небольшой первоначальный набор сервисов для отмены.
- Для каждого выбранного сервиса определить подтверждаемый способ отмены: официальный API/интеграция либо официальная страница отмены.
- Зафиксировать контракт данных, необходимый detection engine, и ограничения внешних интеграций.

**Критерий завершения:** для MVP существует технически и юридически допустимый путь получить операции Сбербанка и для выбранного набора сервисов существует подтверждаемый путь отмены. Если это невозможно, реализация соответствующего внешнего контура не начинается.

### Этап 1. Базовый Telegram-контур
**Зависимости:** нет для разработки интерфейсного контура; интеграция с банком — после Этапа 0.

- Telegram webhook/бот.
- Идентификация пользователя по Telegram ID.
- Главное меню.
- Состояния диалога.
- Экраны списка и карточки подписки в пределах PRODUCT.md.
- Подключение/обновление/отключение банковского доступа как пользовательские действия.
- Базовая обработка ошибок и подтверждение перед отменой.

**Критерий завершения:** пользователь может открыть бота, быть однозначно идентифицирован и пройти предусмотренные интерфейсные состояния; подтверждение отмены является отдельным явным действием.

### Этап 2. Банковский коннектор
**Зависимости:** Этап 0 и интерфейсные контракты Этапа 1.

- Авторизация/согласие пользователя через официальный механизм Сбербанка.
- Хранение только технической ссылки на подключение/токен в защищённом хранилище.
- Получение ограниченного периода истории операций.
- Нормализация ответа банка в внутреннюю модель операций.
- Дедупликация по стабильному техническому идентификатору операции, если он предоставлен.
- Обработка истечения доступа, лимитов, ошибок и отзыва разрешения.

**Критерий завершения:** тестовый пользователь может безопасно подключить банк и получить нормализованный набор операций; банковские логины, пароли, SMS-коды и другие секреты пользователя приложением не сохраняются.

### Этап 3. Обнаружение подписок и анализ функционального пересечения
**Зависимости:** Этап 2.

Ввести отдельные прозрачные правила:
- нормализация merchant;
- группировка похожих получателей;
- расчёт интервалов между платежами;
- анализ стабильности суммы и допуска изменения стоимости;
- отбрасывание разовых и явно нерегулярных операций;
- confidence score и объяснение оснований обнаружения;
- группировка найденных сервисов по назначению/категории;
- выявление потенциально дублирующих подписок;
- объяснение функционального пересечения;
- расчёт потенциальной экономии при отказе от одной подписки на основе наблюдаемой стоимости;
- формирование рекомендаций только как предположений, без выдачи их за финансовый совет или гарантированную экономию.

На MVP предпочтительнее детерминированные правила, а не ML: их проще тестировать, объяснять и корректировать.

**Критерий завершения:** на размеченном тестовом наборе система различает регулярные и нерегулярные платежи по заранее заданным критериям; для найденной подписки объяснимы основания; для тестовых групп подписок корректно определяется потенциальное пересечение и воспроизводится расчёт потенциальной экономии.

### Этап 4. Каталог сервисов и отмена
**Зависимости:** Этап 3; конкретные внешние способы отмены должны быть подтверждены на Этапе 0.

Для каждого поддерживаемого сервиса хранить:
- нормализованные merchant-признаки;
- отображаемое название;
- назначение/категорию, необходимую для анализа пересечения;
- признаки функционального пересечения, если они нужны для правил PRODUCT.md;
- URL официальной страницы управления подпиской;
- тип отмены: API / web;
- требования к дополнительной авторизации;
- ожидаемые статусы операции.

API-отмену реализовывать через отдельные адаптеры сервисов. Для web-сценария только открывать официальный путь отмены; не использовать эмуляцию сайта или обход защиты.

**Критерий завершения:** пользователь может открыть найденную подписку и либо выполнить подтверждённую отмену через поддерживаемую официальную интеграцию, либо перейти на официальную страницу отмены. Неподтверждённая отмена не отображается как успешная.

### Этап 5. Сквозной MVP и hardening
**Зависимости:** Этапы 1–4.

- Полный пользовательский сценарий от Telegram до результата отмены.
- Идемпотентность операций отмены.
- Повторный анализ операций без неконтролируемого дублирования данных.
- Отзыв/удаление банковского подключения.
- Обработка сетевых сбоев и неоднозначного результата внешней операции.
- Минимизация финансовых данных и защита секретов.
- Технические и продуктовые метрики без хранения лишних финансовых данных.

**Критерий завершения:** основной сценарий проходит end-to-end на тестовой группе, критические ошибки обрабатываются безопасно, а заявленные автоматические тесты проходят.

## 2. Архитектурные решения и ограничения

### Общая схема

Telegram Bot
→ Backend application layer
→ User & Subscription domain
→ Bank Connector
→ Transaction Normalizer
→ Subscription Detection Engine
→ Service Catalog
→ Cancellation Orchestrator
→ Service Cancellation Connectors

Долгие операции банка и внешних сервисов выполнять асинхронно там, где это необходимо для надёжности Telegram-контуров.

Хранилище:
- пользовательские настройки и состояние;
- найденные подписки;
- минимальный объём нормализованных операций, только если он нужен для повторного анализа и объяснения результата;
- технические ссылки на секреты, но не сами секреты.

Отдельное секретное хранилище:
- access/refresh tokens и ключи интеграций.

### Ключевые решения

**Adapter pattern для внешних систем.**
Банк и каждый сервис отмены изолированы адаптерами. Ядро продукта не должно зависеть от конкретного формата внешнего API.

**Правила вместо ML на MVP.**
Периодичность, сумма, merchant и признаки категории являются прозрачной первой моделью. Анализ функционального пересечения также должен быть детерминированным и объяснимым.

**Контракты между слоями.**
Нормализованная операция, найденная подписка и операция отмены имеют стабильные внутренние контракты. Внешние изменения обрабатываются на границах адаптеров.

**Идемпотентность.**
Запрос отмены имеет внутренний operation ID/idempotency key. Повтор того же действия не создаёт вторую независимую отмену.

**Fail closed.**
Если результат отмены не подтверждён, состояние остаётся «не подтверждено»/эквивалентным ему и не показывается как успешная отмена.

**Ограничение данных.**
Не хранить банковские логины, пароли, SMS-коды и иные секреты. Полную банковскую историю не сохранять без необходимости. Удаление подключения должно удалять/инвалидировать связанные технические данные в пределах принятой политики хранения.

## 4. Стратегия unit, integration и ручных проверок

### Unit

Покрыть:
- нормализацию merchant;
- сравнение сумм с допустимым отклонением;
- расчёт периодичности;
- расчёт confidence score;
- правила отбрасывания разовых платежей;
- дедупликацию операций;
- категоризацию сервиса для целей PRODUCT.md;
- выявление функционального пересечения;
- объяснение потенциального дублирования;
- расчёт потенциальной экономии;
- обязательную маркировку рекомендаций как предположения;
- переходы статусов отмены;
- идемпотентность cancellation operation.

Граничные случаи:
- ежемесячный платёж с изменившейся ценой;
- пропущенный месяц;
- два платежа в одном месяце;
- одинаковая сумма, но разные получатели;
- похожие merchant names;
- возврат и частичный возврат;
- валюта/округление;
- два сервиса одной категории с разной стоимостью;
- частичное функциональное пересечение без уверенности в дублировании;
- отсутствие данных, достаточных для оценки экономии.

### Integration

Использовать sandbox/mock внешних систем, где они доступны.

Проверить:
1. Telegram → backend → пользователь.
2. Backend → банк → получение операций.
3. Банк → normalizer → detection engine.
4. Detection engine → catalog → overlap/savings analyzer.
5. Cancellation orchestrator → service adapter.
6. Ошибку сети при отмене.
7. Истёкший банковский токен.
8. Повтор одного cancellation operation.
9. Отсутствие права на отмену.
10. Неподтверждённый результат отмены.
11. Повторный анализ без дублирования одной операции.
12. Сервис без API отмены с переходом на официальную страницу.

Для банковской интеграции не использовать реальные пользовательские credentials в автоматических тестах.

### Ручные проверки

Перед тестовой эксплуатацией:
- новый пользователь;
- подключение банка;
- пустая история;
- несколько подписок;
- разовые покупки;
- изменение стоимости подписки;
- потенциально дублирующие подписки;
- корректность объяснения потенциального дублирования;
- корректность оценки потенциальной экономии;
- сервис без API отмены;
- сервис с API отмены;
- отказ/ошибка внешнего API;
- отзыв банковского доступа;
- повторный запуск отмены;
- удаление/отключение подключения;
- понятность текста подтверждения отмены;
- отсутствие ложного сообщения об успешной отмене.

## 5. Критерии завершения каждого этапа

| Этап | Definition of Done |
|---|---|
| 0. Реализуемость интеграций | Подтверждены официальный путь к операциям Сбербанка, необходимые права/ограничения и способы отмены выбранного набора сервисов |
| 1. Telegram-контур | Интерфейсные состояния и явное подтверждение отмены проверены тестами/ручными сценариями |
| 2. Банковский коннектор | Операции получаются и нормализуются, секреты не сохраняются, ошибки доступа обрабатываются безопасно |
| 3. Detection + overlap/savings | Размеченный набор распознаётся по заранее заданным критериям; объяснение, пересечение и расчёт потенциальной экономии воспроизводимы тестами |
| 4. Отмена | Для каждого заявленного сервиса есть подтверждённый официальный API-адаптер либо официальная страница отмены; неподтверждённый результат не считается успехом |
| 5. Сквозной MVP | Основной сценарий проходит end-to-end; критические ошибки безопасны; заявленные автоматические тесты проходят |

Порог качества распознавания заранее фиксируется на размеченной выборке. Минимум оцениваются precision и recall, а отдельно — стоимость ложного срабатывания. Для overlap/savings заранее фиксируются тестовые пары сервисов и ожидаемые объяснения/расчёты.

## 6. Риски реализации и способ отката

| Риск | Способ снижения | Откат |
|---|---|---|
| Интеграция Сбербанка недоступна | Проверить официальный механизм до реализации банковского контура | Не включать банковское подключение в рабочий сценарий до появления допустимого пути |
| API сервиса отмены нестабилен | Отдельный адаптер, таймауты, контрактные тесты | Отключить конкретный адаптер и оставить официальную страницу |
| Неверное распознавание подписок | Размеченная выборка, прозрачные правила, confidence threshold | Вернуть предыдущий набор правил или повысить порог |
| Ложное определение функционального дублирования | Явные категории/признаки, тестовые пары, осторожная формулировка | Отключить конкретное правило overlap, сохранив обнаружение подписок |
| Некорректная оценка экономии | Детерминированная формула и тестовые данные | Отключить отображение оценки до исправления, не отменяя подписки автоматически |
| Повторная отмена | Idempotency key и проверка текущего статуса | Заблокировать повторные операции до подтверждения статуса |
| Ошибка внешнего API после отправки запроса | Состояние «не подтверждено» и отдельная проверка статуса | Повторить проверку либо перевести пользователя на официальный интерфейс |
| Утечка токена | Секретное хранилище, минимальные права, ротация | Отозвать токены и отключить соответствующий коннектор |
| Изменение формата операций банка | Версионирование адаптера и контрактные тесты | Приостановить импорт до совместимой версии |
| Регрессия detection engine | Фиксированный regression dataset | Вернуть предыдущую версию правил |
| Проблема с данными | Минимизация хранения и удаление затронутых данных | Удалить затронутые нормализованные данные и переподключить источник |
