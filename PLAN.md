# PLAN.md

## 1. Этапы реализации и зависимости между ними

### Этап 0. Проверка реализуемости интеграций
**Зависимости:** нет.

- Подтвердить официальный механизм доступа к данным Сбербанка, доступные права, формат операций, лимиты и требования к приложению.
- Выбрать небольшой первоначальный набор сервисов для проверки отмены.
- Для каждого сервиса определить: есть ли официальный API отмены; если нет — официальная страница отмены.
- Зафиксировать ограничения хранения и использования финансовых данных.

**Критерий завершения:** существует технически и юридически допустимый путь получить операции Сбербанка и хотя бы один реалистичный путь отмены для первого набора сервисов. Если банковская интеграция недоступна, дальнейшая реализация блокируется до выбора допустимой альтернативы.

### Этап 1. Базовый Telegram-контур
**Зависимость:** Этап 0.

- Telegram webhook/бот.
- Идентификация пользователя по Telegram ID.
- Главное меню.
- Состояния диалога.
- Базовая обработка ошибок.

**Критерий завершения:** пользователь может открыть бота, быть однозначно идентифицированным и пройти основные экраны без банковской интеграции.

### Этап 2. Банковский коннектор
**Зависимость:** Этап 0, частично Этап 1.

- Авторизация/согласие пользователя через официальный механизм банка.
- Хранение технического токена/идентификатора подключения в защищённом хранилище.
- Получение истории операций за ограниченный период.
- Нормализация ответа банка.
- Обработка истечения доступа, лимитов, ошибок и отзыва разрешения.

**Критерий завершения:** тестовый пользователь может безопасно подключить банк и получить нормализованный набор операций; секреты пользователя не сохраняются приложением.

### Этап 3. Движок обнаружения подписок
**Зависимость:** Этап 2.

Ввести отдельный слой правил:
- нормализация merchant;
- группировка похожих получателей;
- расчёт интервалов между платежами;
- анализ стабильности суммы;
- допуск изменения стоимости;
- отбрасывание нерегулярных операций;
- confidence score.

На первом этапе предпочтительнее прозрачные правила, а не ML: их проще тестировать, объяснять пользователю и корректировать.

**Критерий завершения:** на размеченном тестовом наборе система стабильно различает заранее заданные подписки и разовые платежи, а для каждого результата можно объяснить причину обнаружения.

### Этап 4. Каталог сервисов и отмена
**Зависимость:** Этап 3.

Для каждого поддерживаемого сервиса хранить:
- нормализованные merchant-признаки;
- отображаемое название;
- URL официальной страницы управления подпиской;
- тип отмены: API / web;
- требования к дополнительной авторизации;
- ожидаемые статусы операции.

API-отмену реализовывать через отдельные адаптеры сервисов.

**Критерий завершения:** пользователь может открыть найденную подписку и либо выполнить подтверждённую отмену через поддерживаемый API, либо перейти на официальную страницу отмены.

### Этап 5. Сквозной MVP и hardening
**Зависимость:** Этапы 1–4.

- Полный сценарий от Telegram до результата отмены.
- Идемпотентность отмены.
- Повторный анализ операций.
- Отзыв банковского подключения.
- Обработка сетевых сбоев.
- Безопасность и минимизация данных.
- Метрики технических ошибок и продуктовых событий без сохранения лишних финансовых данных.

**Критерий завершения:** весь основной пользовательский сценарий проходит на тестовой группе, критические ошибки обрабатываются безопасно, а тесты проходят стабильно.

## 2. Предлагаемые архитектурные решения и ограничения

### Общая схема

Telegram Bot
→ Backend API / application layer
→ User & Subscription domain
→ Bank Connector
→ Subscription Detection Engine
→ Service Cancellation Connectors

Хранилище:
- пользовательские настройки и состояние;
- нормализованные операции, если их хранение действительно необходимо;
- найденные подписки;
- технические ссылки на защищённые токены.

Отдельное секретное хранилище:
- OAuth/access/refresh tokens и ключи интеграций.

### Ключевые решения

**Adapter pattern для внешних систем.**
Банк и каждый сервис отмены должны быть изолированными адаптерами. Это позволяет добавлять интеграции без изменения ядра.

**Правила вместо ML на MVP.**
Периодичность + близость суммы + стабильность merchant являются прозрачной первой моделью. ML можно добавить после накопления размеченных данных.

**Асинхронная обработка.**
Получение банковской истории и внешние операции могут выполняться фоновыми задачами, чтобы Telegram не зависел от долгих запросов.

**Идемпотентность.**
Запрос отмены должен иметь внутренний operation ID. Повтор запроса не должен создавать две независимые отмены.

**Fail closed.**
Если результат отмены не подтверждён, бот не должен сообщать «подписка отменена».

**Ограничение данных.**
Не хранить банковские логины, пароли, SMS-коды и иные секреты. По возможности хранить агрегированные/нормализованные данные вместо полного массива банковской истории.

## 3. Какие модули, данные и интерфейсы потребуются

### Модули

1. Telegram Bot Interface.
2. Authentication/User Identity.
3. Bank Connection Manager.
4. Bank Operations Importer.
5. Transaction Normalizer.
6. Subscription Detection Engine.
7. Service Catalog.
8. Cancellation Orchestrator.
9. Service Cancellation Adapters.
10. Notification/Status Manager.
11. Secure Token Storage.
12. Audit/Technical Event Logging.
13. Background Job Worker.

### Основные сущности

**User**
- internal user ID;
- Telegram ID;
- timestamps;
- настройки.

**BankConnection**
- user ID;
- provider;
- external connection ID;
- encrypted token reference;
- status;
- timestamps.

**Transaction**
- operation ID;
- date/time;
- normalized merchant;
- amount/currency;
- direction;
- source;
- технический идентификатор для дедупликации.

**Subscription**
- user ID;
- service ID;
- detected merchant;
- typical amount;
- estimated period;
- last payment;
- confidence score;
- status.

**Service**
- service ID;
- display name;
- merchant matching rules;
- cancellation mode;
- official cancellation URL;
- connector configuration.

**CancellationOperation**
- operation ID;
- subscription ID;
- method;
- status;
- created/updated timestamps;
- external operation ID, если предоставляется.

### Интерфейсы

Telegram:
- `/start`;
- список подписок;
- карточка подписки;
- «Отменить»;
- «Подключить банк»;
- «Обновить данные»;
- «Отключить банк».

Внутренние интерфейсы:
- BankProvider;
- TransactionNormalizer;
- SubscriptionDetector;
- CancellationProvider;
- ServiceCatalog.

Внешние:
- Telegram Bot API;
- официальный банковский API/SDK;
- официальные API поддерживаемых сервисов.

## 4. Стратегия unit, integration и ручных проверок

### Unit

Покрыть:
- нормализацию merchant;
- сравнение сумм с допустимым отклонением;
- расчёт периодичности;
- расчёт confidence score;
- правила отбрасывания разовых платежей;
- дедупликацию операций;
- переходы статусов отмены;
- идемпотентность cancellation operation.

Отдельно тестировать граничные случаи:
- ежемесячный платёж с изменившейся ценой;
- пропущенный месяц;
- два платежа в одном месяце;
- одинаковая сумма, но разные получатели;
- похожие merchant names;
- возврат средств;
- частичный возврат;
- валюта/округление.

### Integration

Использовать sandbox/mock внешних систем, где они доступны.

Проверить:
1. Telegram → backend → пользователь.
2. Backend → банк → получение операций.
3. Банк → нормализация → detection engine.
4. Detection engine → каталог сервисов.
5. Cancellation orchestrator → service adapter.
6. Ошибку сети при отмене.
7. Истёкший банковский токен.
8. Повтор одного cancellation operation.
9. Отсутствие права на отмену.
10. Неподтверждённый результат отмены.

Для банковской интеграции не использовать реальные пользовательские credentials в автоматических тестах.

### Ручные проверки

Перед тестовой эксплуатацией:
- новый пользователь;
- подключение банка;
- пустая история;
- несколько подписок;
- разовые покупки;
- изменение стоимости подписки;
- сервис без API отмены;
- сервис с API отмены;
- отказ/ошибка внешнего API;
- отзыв банковского доступа;
- повторный запуск отмены;
- удаление/отключение подключения;
- понятность текста подтверждения отмены.

## 5. Критерии завершения каждого этапа

| Этап | Definition of Done |
|---|---|
| Проверка интеграций | Подтверждены API/права/ограничения банка и выбранных сервисов |
| Telegram-контур | Основные состояния бота работают, пользователь определяется по Telegram ID |
| Банковский коннектор | Операции получаются и нормализуются, секреты не сохраняются |
| Detection Engine | Тестовый набор распознаётся по заданным критериям качества |
| Отмена | Все заявленные сервисы имеют работающий API-адаптер или официальную ссылку отмены |
| Сквозной MVP | Основной сценарий проходит end-to-end; критические ошибки безопасны; тесты стабильны |

Качество распознавания следует зафиксировать до запуска тестовой группы отдельными метриками precision/recall на размеченной выборке. Порог не следует выбирать «на глаз»: его нужно определить на тестовых данных и отдельно проверить стоимость ложного срабатывания.

## 6. Риски реализации и способ отката

| Риск | Способ снижения | Откат |
|---|---|---|
| Интеграция Сбербанка недоступна | Проверить до разработки основного ядра | Остановить банковский контур и не переходить к production-подключению |
| API сервиса отмены нестабилен | Адаптер + таймауты + контрактные тесты | Отключить конкретный cancellation adapter и оставить официальную страницу |
| Неверное распознавание подписок | Прозрачные правила + тестовая выборка + пороги confidence | Повысить порог или временно отключить автоматическое предложение отмены |
| Повторная отмена | Idempotency key и проверка текущего статуса | Заблокировать повторные операции до подтверждения статуса |
| Ошибка внешнего API после отправки запроса | Хранить состояние «не подтверждено», не считать отмену успешной | Повторить проверку статуса либо перевести пользователя на официальный интерфейс |
| Утечка токена | Секретное хранилище, шифрование, минимальные права | Немедленно отозвать токены и отключить соответствующий коннектор |
| Изменение формата операций банка | Версионирование адаптера и контрактные тесты | Отключить импорт до совместимой версии, не удаляя уже сохранённые состояния подписок |
| Регрессия detection engine | Фиксированный regression dataset | Вернуть предыдущую версию правил |
| Проблема с данными | Ограниченное хранение и возможность удаления | Удалить затронутые нормализованные данные и переподключить источник |
